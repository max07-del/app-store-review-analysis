# Сценарій відеодемонстрації

Орієнтовна тривалість: 5–7 хвилин. Мова — українська.

## Перед записом

```bash
source .venv/bin/activate
export ANTHROPIC_API_KEY=sk-ant-...   # щоб показати LLM-шар
pytest -q                             # показати, що 55 тестів проходять
```

Відкрити заздалегідь: термінал, `reports/nebula/REPORT.md`, браузер.

---

## 1. Вступ (30 с)

«Привіт! Це тестове завдання для позиції AI Engineer в OBRIO — REST API для
збору й аналізу відгуків з Apple App Store. Написано на Python і FastAPI,
запускається локально однією командою.

Ключове рішення, про яке розкажу окремо, — це два шари аналізу: детермінований
NLP-baseline і опційний шар інсайтів на Claude.»

## 2. Архітектура (60 с)

Показати структуру проєкту й пояснити межі відповідальності:

- `apple_client.py` — уся інтеграція з Apple: валідація застосунку, пагінація,
  ретраї на 429 і 5xx, мапінг помилок;
- `review_collector.py` — дедуплікація за ID і випадкова вибірка з сідом;
- `text_analysis.py` — очищення тексту, VADER-сентимент, метрики, ключові слова;
- `llm_insights.py` — шар інсайтів на Claude, повністю ізольований;
- `repository.py` — збереження в SQLite;
- `report.py` — HTML- і Markdown-звіти.

«Аналітичне ядро — синхронне й чисте, тому тестується без мережі.»

## 3. CLI (45 с)

«У завданні просили скрипт для збору 100 випадкових відгуків. Ось він —
працює без сервера:»

```bash
python scripts/collect_reviews.py 1459969523 --country gb --count 100 --seed 42 \
    --output reports/nebula
```

Показати вивід: середній рейтинг, розподіл рейтингів і сентименту, топ
негативних термінів. Наголосити на `--seed`: той самий сід дає той самий
результат.

## 4. Запуск API (30 с)

```bash
uvicorn app.main:app --reload
```

Відкрити `http://127.0.0.1:8000/docs` — показати Swagger.
Показати `/health`: поле `llm_insights` каже, чи активний LLM-шар.

## 5. Створення аналізу (90 с)

У Swagger виконати `POST /api/v1/analyses`:

```json
{ "app": "1459969523", "country": "gb", "count": 100, "seed": 42, "use_llm": true }
```

Пройтись по відповіді:

1. `metrics` — середній рейтинг, розподіл рейтингів і сентименту;
2. `negative_keywords` — часті слова й фрази з негативних відгуків;
3. `insights` — правила: проблемні області з кількістю підтверджень;
4. `llm_insights` — теми з цитатами-доказами, severity, і пріоритезовані
   рекомендації з очікуваним впливом.

«Зверніть увагу: перші три блоки — детерміновані. Четвертий — від моделі.»

## 6. Ключове рішення: два шари (60 с)

«Чому не віддати все моделі? Сентимент по 100 відгуках — це те, що лексикон
робить миттєво, безкоштовно й однаково при кожному запуску. Модель тут додала б
вартість і недетермінованість без виграшу.

А от кластеризація скарг у теми, яких ніхто не прописав наперед, з цитатами й
оцінкою серйозності — це те, чого словник ключових слів не вміє в принципі.

Тому правила дають гарантії, модель дає глибину. І якщо ключа немає або
спрацював rate limit — відповідь приходить повна, просто з попередженням
`LLM_UNAVAILABLE`. Показати це можна так:»

Зупинити сервер, запустити його без ключа й повторити той самий запит:

```bash
unset ANTHROPIC_API_KEY && uvicorn app.main:app
```

Показати, що `llm_insights` тепер `null`, у `warnings` зʼявився
`LLM_UNAVAILABLE`, а метрики, сентимент і ключові слова не змінилися —
детермінована частина не залежить від моделі.

(Окремо: `"use_llm": false` просто вимикає шар без попередження — це свідомий
вибір користувача, а не збій.)

## 7. Безпека: prompt injection (45 с)

«Тексти відгуків пише хто завгодно, і вони йдуть прямо в промпт. Тому вони
загорнуті в теги `<reviews>`, системний промпт каже, що всередині — дані, а не
інструкції, а самі теги всередині відгуку знешкоджуються перед складанням
промпту.

Це не припущення — на це є тест:»

```bash
pytest tests/test_llm_insights.py -k injection -v
```

## 8. Дані та звіти (45 с)

Показати:

- `GET /api/v1/analyses/{id}/reviews` — оброблені відгуки;
- CSV та JSON download;
- `/api/v1/analyses/{id}/report` у браузері — графіки рейтингів і сентименту,
  секція LLM-інсайтів із цитатами;
- `reports/nebula/REPORT.md` — готовий демо-звіт.

## 9. Обробка помилок (30 с)

Показати структуровані помилки:

```bash
curl -X POST .../analyses -d '{"app":"instagram"}'        # INVALID_APP_IDENTIFIER
curl -X POST .../analyses -d '{"app":"999999999999"}'     # APP_NOT_FOUND
curl .../analyses/nope                                     # ANALYSIS_NOT_FOUND
```

«Один формат помилки на весь API.»

## 10. Тести й деплой (30 с)

```bash
pytest -q      # 55 тестів, без мережі
ruff check .
```

Показати `render.yaml`, `fly.toml`, `Procfile` і Dockerfile — образ працює від
non-root користувача й читає `$PORT`.

## 11. Завершення (30 с)

«Підсумую: API збирає й аналізує відгуки, рахує метрики, робить сентимент,
знаходить теми скарг і дає пріоритезовані рекомендації. Є CLI, тести, Swagger,
збереження, експорт даних, візуальні звіти й конфіги для деплою.

Для production я б виніс збір у фонову чергу, замінив англомовний лексикон на
оцінену multilingual-модель і додав відстеження тем у часі, щоб бачити регресії
після релізів. Дякую!»
